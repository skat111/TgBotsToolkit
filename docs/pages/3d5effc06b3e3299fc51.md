# Phone calls

Source: https://core.telegram.org/api/calls

Telegram supports E2E-encrypted one-to-one calls.

This page describes the API methods used to work with calls.

### One-to-one calls

See [here »](https://core.telegram.org/api/end-to-end/video-calls) for a detailed description of the end-to-end encryption used for one-to-one calls, briefly re-explained below with some additional, API-level details:

1. User *A* invokes [phone.requestCall](https://core.telegram.org/method/phone.requestCall) to call user *B*, passing the initial DH parameters and [phone call protocol information »](https://core.telegram.org/api/calls#populating-phonecallprotocol). Set the `video` flag to request a video call, otherwise an audio call is requested.  
   The method will return a [phone.phoneCall](https://core.telegram.org/constructor/phone.phoneCall) with a [phoneCallWaiting](https://core.telegram.org/constructor/phoneCallWaiting)
2. The Server *S* performs privacy checks and sends an [updatePhoneCall](https://core.telegram.org/constructor/updatePhoneCall) update with a [phoneCallRequested](https://core.telegram.org/constructor/phoneCallRequested) constructor to all of *B*'s active devices.
3. Optionally, when *B* receives the [phoneCallRequested](https://core.telegram.org/constructor/phoneCallRequested), *B* may choose to invoke [phone.receivedCall](https://core.telegram.org/method/phone.receivedCall): this will prevent other users from calling *B* until the current call is discarded (either refused, or accepted, confirmed and then discarded), as the server will immediately reject incoming calls with a `reason` equal to [phoneCallDiscardReasonBusy](https://core.telegram.org/constructor/phoneCallDiscardReasonBusy).  
   This step is not strictly necessary, and may be omitted for example by userbot webradios: this will allow multiple users to establish multiple parallel calls with the same user.
4. User *B* accepts the call on one of their devices, performs all the required security checks, and invokes the [phone.acceptCall](https://core.telegram.org/method/phone.acceptCall) method passing DH parameters and [phone call protocol information »](https://core.telegram.org/api/calls#populating-phonecallprotocol): this method will return a [phone.phoneCall](https://core.telegram.org/constructor/phone.phoneCall) with a [phoneCallAccepted](https://core.telegram.org/constructor/phoneCallAccepted).  
   User *B* may also choose to refuse the call instead, using [phone.discardCall](https://core.telegram.org/method/phone.discardCall) with [phoneCallDiscardReasonMissed](https://core.telegram.org/constructor/phoneCallDiscardReasonMissed) (user *A* can do the same as well).
5. The Server *S* sends an [updatePhoneCall](https://core.telegram.org/constructor/updatePhoneCall) with the [phoneCallDiscarded](https://core.telegram.org/constructor/phoneCallDiscarded) constructor to all other devices *B* has authorized, to prevent accepting the same call on any of the other devices. From this point on, the server *S* works only with the specific device owned by *B* that invoked [phone.acceptCall](https://core.telegram.org/method/phone.acceptCall) first.
6. The Server *S* sends to *A* an [updatePhoneCall](https://core.telegram.org/constructor/updatePhoneCall) update with a [phoneCallAccepted](https://core.telegram.org/constructor/phoneCallAccepted) constructor: *A* performs all the usual security checks, then invokes the [phone.confirmCall](https://core.telegram.org/method/phone.confirmCall) method passing DH parameters and [phone call protocol information »](https://core.telegram.org/api/calls#populating-phonecallprotocol): the method will return a [phone.phoneCall](https://core.telegram.org/constructor/phone.phoneCall) with a [phoneCall](https://core.telegram.org/constructor/phoneCall).  
   Then, *A* hands off the call to the tgcalls library using the [phoneCallProtocol](https://core.telegram.org/constructor/phoneCallProtocol) and [phoneConnectionWebrtc](https://core.telegram.org/constructor/phoneConnectionWebrtc) constructors contained in the [phoneCall](https://core.telegram.org/constructor/phoneCall) constructor.
7. The Server *S* sends to *B* an [updatePhoneCall](https://core.telegram.org/constructor/updatePhoneCall) update with the [phoneCall](https://core.telegram.org/constructor/phoneCall) constructor: at this point *B* performs all the required security checks, and hands off the call to the tgcalls library as above.
8. To hang up the call, invoke [phone.discardCall](https://core.telegram.org/method/phone.discardCall), which will emit an [updatePhoneCall](https://core.telegram.org/constructor/updatePhoneCall) with a [phoneCallDiscarded](https://core.telegram.org/constructor/phoneCallDiscarded) for both users.  
   Set the `video` flag if at least one of the two sides of the discarded call has a video stream enabled (regardless of whether initially the call was a video call or a voice call), or when migrating to a [conference call »](https://core.telegram.org/api/calls#migrating-to-a-conference-call).  
   If the [phoneCallDiscarded](https://core.telegram.org/constructor/phoneCallDiscarded).`need_rating` flag is set, the client must invite the user to [rate the call »](https://core.telegram.org/api/calls#call-rating) when it ends.  
   The user may still rate the call manually by right-clicking on the call service message: in this case, the `user_initiative` flag must be set when invoking [phone.setCallRating](https://core.telegram.org/method/phone.setCallRating).

### Migrating to a conference call

```

---functions---

phone.createConferenceCall#7d0444bb flags:# muted:flags.0?true video_stopped:flags.2?true join:flags.3?true random_id:int public_key:flags.3?int256 block:flags.3?bytes params:flags.3?DataJSON = Updates;
phone.discardCall#b2cbc1c0 flags:# video:flags.0?true peer:InputPhoneCall duration:int reason:PhoneCallDiscardReason connection_id:long = Updates;
```

An ongoing one-to-one call may be upgraded ("migrated") to an E2E-encrypted [conference call »](https://core.telegram.org/api/group-calls#conference-calls), for example in order to add more participants.

Migration is only possible if the other party's client supports conference calls, as indicated by the [phoneCall](https://core.telegram.org/constructor/phoneCall).`conference_supported` flag (set by the server in the final [phoneCall](https://core.telegram.org/constructor/phoneCall) constructor): clients should only offer the migrate/"Add participants" option in the call UI when this flag is set.

To migrate the call, the initiating client:

1. Creates a new conference call by invoking [phone.createConferenceCall](https://core.telegram.org/method/phone.createConferenceCall) with the `join` flag set, joining the freshly created conference itself as described [here »](https://core.telegram.org/api/group-calls#conference-calls); the current call's media state (mute and camera/video status) is carried over to the new conference.
2. Extracts the [conference deep link »](https://core.telegram.org/api/links#conference-links) slug from the returned [groupCall](https://core.telegram.org/constructor/groupCall).`invite_link`.
3. Discards the one-to-one call by invoking [phone.discardCall](https://core.telegram.org/method/phone.discardCall) with a [phoneCallDiscardReasonMigrateConferenceCall](https://core.telegram.org/constructor/phoneCallDiscardReasonMigrateConferenceCall) `reason`, passing the conference slug in its `slug` field (as for any discarded call, also set the `video` flag if either side had a video stream enabled).

The other party then receives an [updatePhoneCall](https://core.telegram.org/constructor/updatePhoneCall) with a [phoneCallDiscarded](https://core.telegram.org/constructor/phoneCallDiscarded) whose `reason` is a [phoneCallDiscardReasonMigrateConferenceCall](https://core.telegram.org/constructor/phoneCallDiscardReasonMigrateConferenceCall): it must extract the `slug`, fetch the newly created conference call by invoking [phone.getGroupCall](https://core.telegram.org/method/phone.getGroupCall) with an [inputGroupCallSlug](https://core.telegram.org/constructor/inputGroupCallSlug) generated from the slug, and automatically join it as described [here »](https://core.telegram.org/api/group-calls#conference-calls), again carrying over the previous call's media state.

This effectively moves both users from the one-to-one call into the new conference call, where additional users can then be [invited »](https://core.telegram.org/api/group-calls#conference-calls).

### Populating `phoneCallProtocol`

```
phoneCallProtocol#fc878fc8 flags:# udp_p2p:flags.0?true udp_reflector:flags.1?true min_layer:int max_layer:int library_versions:Vector<string> = PhoneCallProtocol;
```

[phoneCallProtocol](https://core.telegram.org/constructor/phoneCallProtocol) describes the tgcalls protocol versions supported by the local build of tgcalls, populated as follows:

* fill `library_versions` with the ordered list of supported tgcalls protocol versions (order matters, the preferred tgcalls protocol version must come first)
* set both `udp_p2p` and `udp_reflector` to true (deprecated, previously used to allow or disallow the use of direct peer-to-peer networking for libtgvoip calls)
* set `min_layer` to `65` (deprecated, was previously used to describe the oldest supported libtgvoip protocol)
* set `max_layer` to `92` (deprecated, was previously used to describe the newest supported libtgvoip protocol)

`udp_p2p`, `udp_reflector`, `min_layer` and `max_layer` were previously used by the deprecated libtgvoip library, and should not be passed to tgcalls: the values listed here are hardcoded and immutable, fixed to the last values supported by libtgvoip and are only used if the other end still uses libtgvoip.

The use of peer-to-peer networking is now controlled by the [privacyKeyPhoneP2P](https://core.telegram.org/constructor/privacyKeyPhoneP2P) [privacy setting »](https://core.telegram.org/api/privacy), which is used by the server to choose whether to also return P2P STUN [phoneConnectionWebrtc](https://core.telegram.org/constructor/phoneConnectionWebrtc) connection options, along with the usual reflector TURN [phoneConnectionWebrtc](https://core.telegram.org/constructor/phoneConnectionWebrtc) connection options.

The same local capability set is re-sent in all three outbound handshake methods: the `protocol` embedded in [phoneCallWaiting](https://core.telegram.org/constructor/phoneCallWaiting), [phoneCallRequested](https://core.telegram.org/constructor/phoneCallRequested) and [phoneCallAccepted](https://core.telegram.org/constructor/phoneCallAccepted) does not stop either client from advertising its own local capabilities again in the next outgoing RPC.

### Signaling data

```
updatePhoneCallSignalingData#2661bf09 phone_call_id:long data:bytes = Update;

---functions---

phone.sendSignalingData#ff7a9383 peer:InputPhoneCall data:bytes = Bool;
```

[phone.sendSignalingData](https://core.telegram.org/method/phone.sendSignalingData) is only used after the DH handshake is over and both sides have the final [phoneCall](https://core.telegram.org/constructor/phoneCall) with verified key material and connection info: at this point, tgcalls should be initialized from the final [phoneCall](https://core.telegram.org/constructor/phoneCall) constructor's `protocol` and `connections` fields, and only then tgcalls's signaling callback can be wired to invoke [phone.sendSignalingData](https://core.telegram.org/method/phone.sendSignalingData).

Invoke this method whenever the tgcalls emits an opaque signaling packet that must be delivered to the peer: this will emit an [updatePhoneCallSignalingData](https://core.telegram.org/constructor/updatePhoneCallSignalingData) for the other peer in the call, who should then pass [updatePhoneCallSignalingData](https://core.telegram.org/constructor/updatePhoneCallSignalingData).`data` to their own instance of tgcalls.

### Call rating

```
---functions---

phone.setCallRating#59ead627 flags:# user_initiative:flags.0?true peer:InputPhoneCall rating:int comment:string = Updates;
```

Invoke [phone.setCallRating](https://core.telegram.org/method/phone.setCallRating) after the call ends to rate the call (sending a message to the official VoIP rating bot), passing the following parameters:

* `peer`: The [inputPhoneCall](https://core.telegram.org/constructor/inputPhoneCall) generated from the [phoneCallDiscarded](https://core.telegram.org/constructor/phoneCallDiscarded)
* `user_initiative`: Set this flag if the rating was initiated by the user by right-clicking on the call service message; must NOT be set if rating was requested by the server with [phoneCallDiscarded](https://core.telegram.org/constructor/phoneCallDiscarded).`need_rating`.
* `rating`: A score from 1 to 5, chosen by the user.
* `comment`: A user-specified comment (only for ratings not equal to 5).

  The user may also choose to report additional problems from the following fixed list, in the form of `#hashtags` appended to the comment.

  These hashtags may be appended even for ratings equal to 5, using this algorithm:

  + If the accumulated comment is not empty, append a whitespace
  + Append the ID of the chosen problem as a hashtag (i.e. `#echo`)
  + Repeat for all problems chosen by the user, from the following available options:

#### Call rating problem types

##### `echo`

The user heard their own voice (echo).

##### `noise`

The user heard background noise.

##### `interruptions`

The other side kept disappearing.

##### `distorted_speech`

The speech was distorted.

##### `silent_local`

The user couldn't hear the other side.

##### `silent_remote`

The other side couldn't hear the user.

##### `dropped`

The call ended unexpectedly.

##### `distorted_video`

The video was distorted.

##### `pixelated_video`

The video was pixelated.
